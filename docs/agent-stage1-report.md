# Отчёт по этапу 1: рабочее окружение Codex на home-server

**Статус:** завершён  
**Цель этапа:** подготовить отдельную учётную запись и устойчивое рабочее пространство для Codex CLI на домашнем сервере, сохранив существующий административный SSH workflow и ручной контроль системных изменений.

## Краткий итог

На сервере создан пользователь `agent` с отдельным домашним каталогом и минимальными группами. В его профиле доступны Codex CLI и tmux. Пользователь прошёл интерактивный вход в Codex и подтвердил рабочий цикл подключения, запуска tmux и Codex. Для проекта создан отдельный clone и тестовый Git worktree. Инструкция по эксплуатации записана в [`agent-workspace.md`](agent-workspace.md).

Изменения системной конфигурации были внесены в NixOS repository, опубликованы и получены серверной копией. Конфигурацию применил владелец сервера из своего терминала. Агентская учётная запись не получила административных полномочий; развёртывание NixOS из Codex не выполнялось.

## Что было изменено

### NixOS-конфигурация

- Добавлен модуль [`hosts/server/agent-workspace.nix`](../hosts/server/agent-workspace.nix).
- Модуль объявляет приватную группу `agent` и обычного пользователя `agent`.
- Домашний каталог: `/persist/home/agent`, создаётся системой, режим доступа `0700`.
- В дополнительные группы пользователь не включён (`extraGroups = [ ]`).
- В профиль пользователя добавлены пакеты `codex` и `tmux`.
- Модуль подключён из [`hosts/server/default.nix`](../hosts/server/default.nix).

Выбор `/persist` сохраняет домашние данные между перезагрузками в соответствии с устройством хранения сервера. Настройки и авторизация Codex принадлежат учётной записи `agent`.

### Git и рабочие каталоги

В домашнем каталоге `agent` организованы каталоги для постоянных clone и отдельных рабочих деревьев:

```text
~/repos/       основные clone репозиториев
~/worktrees/   отдельные Git worktrees для задач
```

Пользователь сервера подтвердил создание и чистое состояние следующих копий:

```text
~/repos/NixOS-Config
~/worktrees/NixOS-Config-stage1-smoke
```

Тестовый worktree использует ветку `codex/stage1-smoke`, отслеживающую `origin/master`. Владелец сервера сообщил результат `git status --short --branch`:

```text
## codex/stage1-smoke...origin/master
```

Этот smoke worktree предназначен для проверки рабочего пространства. Он не является активной копией конфигурации, применённой системой.

### Документация

В [`docs/agent-workspace.md`](agent-workspace.md) записаны подключение через существующий alias `home-server`, вход в `agent`, tmux, запуск Codex, Git worktree workflow, границы доступа и базовая диагностика.

## Развёртывание и Git-история

1. Изменение конфигурации было оформлено коммитом `fd6ee58` (`feat: add isolated Codex workspace`), опубликовано и получено на сервере.
2. Владелец сервера применил конфигурацию из своего терминала; активацию выполнял не Codex.
3. Инструкция и подтверждённые сведения о smoke worktree добавлены коммитом `032648d` (`docs: record verified agent worktree`).
4. Последний `pull --ff-only` на серверную копию завершился успешно.
5. Последняя проверка показала, что локальная и серверная копии `NixOS-Config` находятся на `032648d`. Локальная ветка `master` отслеживала `NixOS-Config/master`, серверная `master` — `origin/master`; обе были чистыми.

Локальный файл дорожной карты `agentic-homelab-roadmap.md` оставался незакоммиченным и не включался в эти изменения.

## Проверки и наблюдения

### На сервере

По результатам read-only проверки после применения конфигурации:

- система сообщала выпуск NixOS `26.05.20260901.a311611`;
- UID/GID пользователя и членство в группе соответствовали отдельной учётной записи `agent`;
- домашний каталог имел владельца `agent:agent` и режим `0700`;
- Codex CLI сообщал версию `0.146.0`;
- tmux сообщал версию `3.6a`;
- владелец сервера подтвердил интерактивный вход в Codex и работу сессии.

Версия Codex сообщала о доступном обновлении до `0.170.0`. По решению владельца обновление отложено; в этом этапе оно не выполнялось.

### Сборка конфигурации без активации

Успешно выполнена неактивирующая сборка целевого system closure через Nix. Она подтвердила, что объявленная конфигурация собирается. Сборка скачала 13 store paths: около 146,2 MiB загрузки и 475,6 MiB после распаковки. Измеренный closure Codex составлял около 517,5 MiB. На момент проверки свободное место составляло около 30 GiB в `/nix` и 4,8 GiB в `/tmp`.

Это данные на момент проверки, а не постоянная гарантия свободного места. Сборка не переключала поколение NixOS и сама по себе не доказывает корректность всех эксплуатационных сценариев.

### Git worktree workflow

Последовательность создания отдельной ветки и worktree предварительно проверялась на временном локальном тестовом репозитории, а затем smoke worktree был создан владельцем на сервере. Рабочее дерево было сообщено чистым и ветка отслеживала ожидаемую базовую ветку.

## Модель доступа и безопасности

- Codex запускается от непривилегированного пользователя `agent`.
- По проверенному членству в группах `agent` не состоит в `wheel` или `networkmanager` и не получает административные права через группу.
- Домашний каталог `agent` закрыт от доступа других пользователей режимом `0700`.
- Рабочие clone/worktree отделены от административного checkout `/home/server/NixOS-Config`.
- В документации указано не копировать в `agent` учётные данные пользователя `server` и не помещать API-ключи в Git или shell history.
- Агенту не предоставлялись SSH credentials, age-ключи, доступ к Docker/Podman socket или право активировать конфигурацию NixOS.
- Clone репозитория агента получен по HTTPS. В flake есть private input, к которому у `agent` нет доступа; полная проверка flake от имени `agent` требует отдельного решения администратора.
- Для обычного SSH-подключения используется уже существующий alias `home-server`; сетевые настройки, reverse tunnel и SSH-сервер в рамках этапа не менялись.

Отдельный Unix-пользователь ограничивает доступ к домашним данным и привилегиям, но не является полной изоляцией ядра. Поэтому системные, сетевые и другие привилегированные операции остаются под контролем владельца сервера.

## Ограничения и оставшиеся пункты

- Полноценная реальная задача разработки в отдельном worktree, с diff, проверками и независимым review, ещё не проведена. Smoke worktree подтверждает организацию каталога и Git-связей, но не заменяет такой рабочий цикл.
- Обновление Codex до `0.170.0` отложено.
- Полный flake evaluation для пользователя `agent` не проводился из-за недоступного private input.
- Восстановление самой tmux-сессии после перезагрузки не обещается; сохраняются файлы в `/persist`, а сессию после reboot нужно запустить снова.
- Этап не добавлял оркестратор, автоматическое развёртывание, автоматические approvals или автоматическое применение системной конфигурации.

## Риски и откат

Основной операционный риск — ошибки в будущих задачах, выполняемых агентом с доступом на запись к своим clone/worktree. Их изменения должны оставаться в отдельной ветке и проходить review до слияния. Ошибка в декларативном модуле может повлиять на вход пользователя `agent` или доступность его инструментов, но не должна давать ему системные полномочия.

Откат конфигурационного изменения выполняет администратор: удалить импорт модуля и сам модуль из NixOS checkout, проверить конфигурацию, затем применить её по обычной процедуре сервера. Такое удаление и активация в рамках этого отчёта не выполнялись. Данные `/persist/home/agent` не следует удалять как часть отката без отдельного решения владельца.

## Следующий шаг дорожной карты

Перейти к этапу 2 в минимальном объёме: выбрать небольшую, ограниченную и проверяемую задачу; сформулировать критерии приёмки; выполнить её в отдельном worktree и ветке; представить diff и результаты проверок; провести review до любого слияния или развёртывания. Сначала стоит проверить практическую передачу задачи и артефактов между ролями вручную, не строя оркестратор.
