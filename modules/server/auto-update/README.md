# Автоматические обновления NixOS

В этой директории находится серверный фундамент консервативного механизма
автообновлений. Он подключён через `hosts/server/default.nix`, но пока не
является законченным updater: ни сборка, ни активация generation не выполняются.

## Что есть сейчас

- `fetch.nix` создаёт `nixos-update-fetch.service` и таймер раз в пять минут.
  Сервис запрашивает текущую ревизию `master` и соответствующий ей push-запуск
  `nixos.yml` в GitHub. Результат атомарно записывается в
  `/var/lib/nixos-auto-update/github` в формате JSON.
- `health-check.nix` создаёт `nixos-health-check.service`. Содержательных
  проверок в нём пока нет, поэтому он публикует пустой успешный результат.
  Контракт результата — JSON-файл `/var/lib/nixos-auto-update/health`:

  ```json
  {
    "checked_at": "время в RFC 3339",
    "critical": 0,
    "major": 0,
    "minor": 0,
    "errors": []
  }
  ```

  Будущие проверки должны добавлять структурированные записи в `errors` и
  обновлять счётчики. Critical завершается кодом 2, major — кодом 1,
  здоровый/minor-only результат — кодом 0. Подробности следует читать только
  из JSON, а не разбирать текст journal.

Каталог состояния доступен только root и создаётся `systemd-tmpfiles`. Оба
текущих сервиса лишь публикуют данные и не меняют generation NixOS.

## Целевая машина состояний

`fetch` только наблюдает за GitHub. Будущий сервис `update` — единственный
писатель состояния развёртывания и единственный компонент, которому вообще
разрешены активация и откат generation.

```text
GitHub + успешный CI -> кандидат -> активированный кандидат -> probation
                                                        |          |
                                                        |          +-- несколько успешных проверок -> stable
                                                        +-- critical / устойчивый major -> откат к stable
```

`update` должен хранить собственный атомарный JSON как минимум с:

- последними подтверждённо стабильными revision и NixOS generation;
- revision и generation активного кандидата;
- временем активации кандидата и ограниченной историей health-проверок;
- revision, отклонёнными после отката, чтобы не ставить их повторно;
- необязательным административным флагом паузы.

## План продолжения

1. Определить конкретные health-проверки и их severity. У каждой должны быть
   тайм-аут, детерминированный вывод и отдельная политика для переходных
   состояний после загрузки.
2. Реализовать машину состояний `update` сначала без активации: разбирать два
   JSON-входа, записывать решения по кандидатам и покрыть это fixture-файлами.
3. Выбрать способ материализовать точную Git-revision для сборки, не затрагивая
   рабочий checkout пользователя. До начала probation записывать revision и
   получившуюся generation вместе.
4. Добавить общесистемную блокировку и логику rejected-revision/cooldown, затем
   реализовать путь сборки и активации.
5. Выполнить оценку конфигурации и проверить в безопасной среде сценарии:
   успешный CI, незавершённый/упавший CI, переходная ошибка health-check,
   critical-ошибка и rollback. Лишь после этого включать таймер, способный
   активировать обновления.

Любая сборка, активация, откат, сетевая проверка или изменение сервисов,
критичных для связности, требует отдельного операционного review перед
включением на сервере.
